- **bngsim read and wrote text in the locale's encoding, so a UTF-8 `.bngl` failed to load where the locale is ASCII, and was misread under Latin-1 or Windows' cp1252 ([#1665](https://github.com/lanl/bngsim/issues/1665)).** One non-ASCII character, even an em dash in a comment, made `Model.from_bngl` raise a bare `UnicodeDecodeError`; 83 of the 895 BNGL files in the parity models have one. Every text file bngsim opens, and the output of BNG2.pl it reads, is now UTF-8: 33 places, 7 of which ruff's `PLW1514` does not see. That includes what bngsim writes: `Result.to_csv`, `.gdat`/`.cdat`, `.net`, BNGL and SED-ML files are UTF-8 on every platform, where on Windows they were in the ANSI code page. A `.bngl` with a byte that is not UTF-8 (a Latin-1 comment) is handed to BNG2.pl as it is. A compiler's output is read in the platform's encoding (the ANSI code page on Windows, UTF-8 elsewhere). Output that is not valid has its bad bytes replaced, so BNG2.pl's own error is shown, not a decode error. A test reads the package's source and fails on a text-mode open that names no encoding, so the next one is caught.
